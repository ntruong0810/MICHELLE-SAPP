1. PROJECT GOAL

Michelle's Day Planner is intended to be a simple, cute digital paper planner: a quiet place to write down plans, not a conventional project-management application. The experience should resemble a warm paper calendar or stationery page, with direct writing surfaces and restrained controls instead of cards, metrics, workflows, assignees, or dashboard chrome.

The Month view is the broad planning surface. It shows a complete Sunday-first month grid (including adjacent-month days needed to complete each row), supports several independent notes/events per date, offers a focused-day overlay for overflow, and links each calendar row to its corresponding Week. The Week view is a seven-column page for the selected Sunday-through-Saturday range. It shows Month-created events as read-only canonical items, allows additional Week-only events, and keeps a separate persistent task list with checkboxes for each day.

The central product distinction is between canonical Month events, Week-only events, and Week-only tasks. They share dates but are not interchangeable records. Photos/media are currently being added in the uncommitted working tree; that implementation is only partial.

6. DATABASE / SUPABASE ARCHITECTURE

calendar_events (supabase/calendar_events.sql)
- Purpose: canonical Month-created events/notes. Week reads these same rows.
- Ownership: user_id UUID defaults to auth.uid(), references auth.users(id), and cascades on user deletion.
- Columns: id UUID default gen_random_uuid(), user_id, date, content, sort_order, created_at, updated_at.
- Index: (user_id, date, sort_order).
- Trigger: set_calendar_event_updated_at updates updated_at before update.
- RLS/grants: anon has table privileges revoked; authenticated receives select/insert/update/delete. Each RLS policy requires auth.uid() = user_id.

weekly_only_events (supabase/weekly_only_events.sql)
- Purpose: events created directly in one Week; never queried by Month.
- Columns: id, user_id, date, week_start, content, sort_order, created_at, updated_at.
- Index: (user_id, week_start, date, sort_order).
- Ownership, trigger, grants, and RLS follow the same authenticated-user pattern as calendar_events.

weekly_tasks (supabase/weekly_tasks.sql)
- Purpose: Week-only checklist records.
- Columns: id, user_id, date, week_start, content, is_completed (default false), sort_order, created_at, updated_at.
- Index: (user_id, week_start, date, sort_order).
- Ownership, trigger, grants, and RLS follow the same authenticated-user pattern.

planner_media (uncommitted supabase/planner_media.sql)
- Purpose: per-date metadata for either an uploaded photo or a built-in sticker.
- Columns: id, user_id, date, kind, storage_path, sticker_key, created_at.
- Constraint: photo rows require storage_path and forbid sticker_key; sticker rows require sticker_key and forbid storage_path.
- No geometry columns and no update operation/policy exist.
- Index: (user_id, date, created_at).
- Grants: authenticated select/insert/delete only; anon revoked. RLS restricts all operations to auth.uid() = user_id.
- Current UI relationship: Month can load/upload/delete photos for a selected date and can render existing sticker rows. Week loads photo rows for its seven-day range and displays them read-only. Week does not create/delete media.

Storage bucket: planner-photos (uncommitted supabase/planner_media.sql)
- Private bucket, 8 MiB file limit.
- Allowed MIME types: image/jpeg, image/png, image/webp, image/gif.
- Object path convention: {auth user UUID}/{date}/photo-{timestamp}-{random suffix}.{extension}.
- Authenticated select/insert/delete policies require the first storage folder to equal auth.uid().
- The client creates one-hour signed URLs for display.
- On metadata insert failure after upload, the client tries to remove the uploaded object. On metadata deletion, it deletes the row first and then tries to remove the object; storage cleanup failure is logged and may leave an orphan object.

No weekly_event_states table or other planner table exists in the SQL directory. Do not infer that a TypeScript type implies deployed schema. SQL files are setup scripts, not a migration framework, and the repository cannot prove which scripts have been applied remotely.


7. CRITICAL DATA SEMANTICS

CalendarEvent
- Canonical Month event.
- Created, edited, and deleted in Month.
- Appears in its Month date cell and in the corresponding Week by loading the same calendar_events row.
- In Week it is rendered read-only with origin "calendar". Week must not copy it into weekly_only_events or offer Week-local edit/delete semantics.

WeeklyOnlyEvent
- Created directly in Week and scoped by both date and weekStart.
- Appears only in Week.
- Must not automatically appear in Month.
- Can be edited/deleted only through the Week-only record path.

WeeklyTask
- Separate Week-only checklist record; never an event.
- Scoped by date and weekStart.
- Checkbox completion persists in is_completed.
- Must not appear in Month and must not be merged into CalendarEvent.

Composition/order
- resolveWeekEvents combines in-memory CalendarEvent and WeeklyOnlyEvent values only for display, adds origin, and sorts by date/sortOrder with calendar origin before weekly origin on ties.
- A new Week-only event receives the next sortOrder after all displayed events for that date, including canonical Month events.
- Tasks have their own per-day sort order and collection.

Overrides/hide/reset
- Not implemented. WeeklyEventState exists only as an unused TypeScript type. There is no database table, state resolver, control, or persistence flow for override, hide, or reset.

Media
- Current media records belong to a date, not to a specific event/task.
- Current working-tree behavior shows Month-added photos in Week as read-only photo stacks. This differs from the older proposed initial scope of Month/Focused Day only; actual code is authoritative.


8. AUTHENTICATION

lib/supabase/client.ts reads only these public environment names:
- NEXT_PUBLIC_SUPABASE_URL
- NEXT_PUBLIC_SUPABASE_ANON_KEY

app/layout.tsx additionally reads NEXT_PUBLIC_SITE_URL for metadata. .env.example currently lists only the two Supabase variables.

getSupabaseBrowserClient creates one cached browser client with autoRefreshToken: true, persistSession: true, and detectSessionInUrl: false. Each planner data operation calls ensureAnonymousPlannerUser. That function first calls auth.getSession(); if a user is already present, it returns the user ID. Otherwise it coalesces concurrent initialization through one module-level Promise around auth.signInAnonymously(), returns the new anonymous user's ID, and clears that Promise when complete.

Although the user is "anonymous" from the product perspective, Supabase treats a signed-in anonymous user as authenticated. SQL revokes anon table access, grants authenticated access, and RLS matches auth.uid() to row.user_id. Client queries also explicitly filter by user_id. Session persistence means the browser retains ownership across visits; clearing/replacing browser storage may create a different anonymous user who cannot see the former user's rows. Anonymous sign-ins must be enabled in the Supabase project.

No secret/service-role key belongs in this client-side app. Do not put API keys, access tokens, refresh tokens, passwords, or service-role material in documentation or source.


9. PERSISTENCE FLOW

Month event creation
1. The user types in a day and commits by Enter, blur, Tab traversal, or switching writing targets.
2. appendCalendarEvent trims content, ignores blank input, calculates the date's next sortOrder, and creates an optimistic CalendarEvent with a temporary string ID such as event-{timestamp}-{counter}.
3. MonthPlanner appends a create mutation to a serialized in-memory queue and shows Saving.
4. lib/planner-data/calendar-events.ts calls ensureAnonymousPlannerUser and INSERTs user_id/date/content/sort_order without the temporary id.
5. Postgres creates the UUID. The returned row maps back to CalendarEvent (with textSize forced to medium).
6. MonthPlanner replaces the temporary ID in current UI state, any active edit draft, and later queued update/delete operations.

Month edits/deletes are optimistic and queued in order. Updates send date/content/sort_order and scope by id plus user_id. Deletes scope by id plus user_id. A mutation error stops the queue at the failed item, leaves optimistic state in place, displays "Couldn't save," and offers Retry. A load error offers Retry by reloading. There is no automatic rollback of a failed Month update/delete.

Week-only event creation
- submitNewEvent trims/rejects blank content through appendWeeklyOnlyEvent, creates an optimistic temporary ID, computes sortOrder after the day's combined displayed events, clears the input, and calls createWeeklyOnlyEvent.
- The insert omits id, and success replaces the optimistic item with the returned UUID row.
- Edit is optimistic after commit; delete is optimistic. Create/edit failures keep the optimistic/current edited value and offer Retry. Delete failure restores the deleted item. Only Week-only events have edit/delete controls in Week.

Weekly tasks
- Creation mirrors Week-only creation: temporary ID, trimmed content, per-day task sortOrder, isCompleted false, insert without id, replace with returned row.
- Text edits optimistically call updateWeeklyTask.
- Checkbox toggles optimistically invert isCompleted and call toggleWeeklyTask; failure rolls completion back and offers Retry.
- Delete is optimistic; failure restores the task and offers Retry.

Week save/error behavior
- One runSave operation is allowed at a time; controls derive disabled/busy state while loading or saving.
- Initial load uses Promise.allSettled for calendar events, Week-only events, tasks, and photos. Failure of any of the first three makes the Week load state an error and exposes Retry. Photo load failure is logged but deliberately excluded from the visible load-error state.
- Save failures retain a closure in retryActionRef. A load retry increments loadVersion and reloads.

Media
- Photo upload validates JPG/PNG/WebP/GIF and <=8 MiB, uploads to planner-photos, inserts planner_media metadata, creates a signed preview URL, and appends only after success (not optimistic).
- Media deletion optimistically removes the gallery card, deletes the metadata row, then attempts Storage cleanup; metadata failure restores the gallery item.
- Sticker insert support exists in createPlannerSticker, but no component currently calls it.
- Media-panel errors show a message but do not currently offer a dedicated Retry button; the user can repeat the action or reopen the panel.


10. MONTH PLANNER

- Navigation: previous/next month arrows, direct Month/Year selects (current year +/-10), and canonical /month/YYYY/MM routing. Invalid month routes return notFound; /month query parameters redirect after validation.
- Grid: UTC-safe, Sunday-first, complete weeks only; therefore a month can render four, five, or six rows. Adjacent-month days are included and remain writable.
- Events: click/tap a writing area to create; click an event to edit; Enter/blur commit; Escape cancels; delete button removes one event. Blank creates and blank edits are ignored by pure helpers.
- Multiple events: supported independently with monotonically increasing per-date sortOrder. Deletion does not compact sortOrder.
- Overflow: each cell renders at most three records. "N more..." opens FocusedDayOverlay, which renders all records and supports the same core mutations.
- Focused day: modal-like overlay closes from its X, backdrop, or Escape when no draft is active. It is not a media canvas. The separate flower trigger on the cell opens DayMediaPanel for that date.
- Keyboard behavior in the dirty working tree: Tab/Shift+Tab while creating/editing commits and moves to the adjacent visible calendar date, editing that date's first event or starting a new draft. This behavior is unit-uncovered at the component level.
- Persistence: full visible-grid date range is loaded from Supabase. Optimistic queue semantics are described above.
- Week row navigation: each row has a Week link using that row's Sunday. The shell's generic Week tab points to a computed week around the middle of the displayed month, not necessarily today's week.
- Responsive behavior: over 700px the sheet is constrained to 100dvh and each calendar row flexes to share remaining height. Below 701px the sheet loses outer chrome, but the grid keeps min-width 880px and horizontally scrolls. It is not transformed into a mobile list/day view.
- Known limitations: only three events are visible in-cell; media is a separate gallery; textSize is always effectively medium; no drag/reorder; no cross-device conflict handling; no E2E verification.


11. WEEK PLANNER

- Seven-day calculation: buildWeek accepts any valid ISO date, normalizes it to Sunday via UTC methods, and returns Sunday through Saturday. The route renders the normalized Sunday.
- Navigation: previous/next Week arrows, Back to month using the Week's middle (Wednesday) month, and shared Month/Week tabs.
- Month -> Week synchronization: Week loads calendar_events for exactly the selected seven-day range. These Month-derived items are displayed with a bullet and no edit/delete controls. They are not duplicated.
- Week-only events: load by week_start; create under a date; edit content; delete. These have separate controls and never enter Month queries.
- Weekly tasks: load by week_start; create/edit/delete per date; checkbox toggles persistent is_completed; completed content is muted/struck through.
- Events/Tasks divider: every day column shares one percentage split (default 58/42, clamped 20/80). Dragging any separator updates the shared split. ArrowUp/ArrowDown move by 2%; Home/End select bounds. Value persists in localStorage under little-day-planner:week-divider:{weekStart}.
- Photos in current dirty tree: Week also loads photo media for the date range. Each day can show up to three stacked thumbnails representing all available photos; clicking opens a portal-based gallery. Week has no photo add/delete control and ignores stickers.
- Save states: Loading/Saving/Saved/errors appear in the Week tools. Core load or mutation errors offer Retry. Canonical events remain read-only even if the Week-only sections are interactive.
- Responsive behavior: over 700px the Week grid fits the viewport vertically and event/task sections scroll internally. At all widths the grid has min-width 880px (seven columns of at least 126px) and the wrapper horizontally scrolls. Media viewers become bottom-sheet-like and one-column on small screens. lib/week-navigation.ts is not wired, so there is no actual mobile selected-day navigation despite its test name.

15. IMPORTANT BUGS / LESSONS FROM DEVELOPMENT

- Never send temporary UI IDs to UUID database columns. All insert mappers intentionally omit id and reconcile the returned database UUID.
- Local IDs use timestamp/counter or timestamp/random-string construction rather than crypto.randomUUID(). This avoids secure-origin problems on non-secure LAN development origins.
- Month/Week synchronization must load the same canonical calendar_events rows, not duplicate them into Week data.
- Do not restore hardcoded Week demo data. Week derives data from Supabase and pure helpers.
- Keep WeeklyTask separate from CalendarEvent and WeeklyOnlyEvent.
- Week-only events must never appear in Month.
